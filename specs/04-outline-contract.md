# 04 第一阶段的“框架”交付契约

## 1. 核心定义

这里的“框架”是**业务导向的一级/二级标题提纲 + 每章内容方向/待确定点**，不是正文成稿，也不是单纯枚举通用公文标题。

用户第一轮通常给出活动目的和少量相关事项；框架需要及时形成，并可由对话调整。

## 2. 对用户的呈现形式（人类可读）

第一阶段的讨论框架可以合并相关的信息层，降低阅读和确认成本。正式策划案应参照资料库中适用策划案的一级标题，把需要独立呈现的部分拆分出来。

```text
××活动策划案（讨论框架）

一、活动背景及目的

二、活动时间、地点、参与对象及组织单位

三、活动内容与流程
（一）活动事项 A
（二）活动事项 B

四、工作安排
   内容方向：按需说明准备、现场组织和结束整理的分工。

五、所需材料
   内容方向：按本次活动的实际方案整理所需物品。

六、活动注意事项
```

说明：上述仅为降低讨论负担的合并框架示例；实际活动不一定包含全部标题，二级标题也依据真实活动事项设置。定稿时，参照适用案例，把时间、地点、参与对象、主办单位、承办单位等需独立呈现的内容拆分为相应一级标题。示例中的 A、B 只表示用户已经提出的事项，不预设具体流程。

注释规则：活动背景、活动目的、活动时间、活动地点、参与人员等含义清楚的标题通常无需说明。对于“活动内容、工作安排、所需材料”等具体内容方向不明显的标题，可用一句话解释要涵盖的大致内容。解释只指出信息范围，不推定具体方案；注释无法提供清楚帮助时可以省略。

## 3. 生成框架的判定顺序

1. 列出用户已确认事实、建议性想法和未知信息。
2. 从本次活动目标倒推必须完成的活动动作。
3. 对活动动作识别执行条件、责任、关键风险、成果交付。
4. 参考学校案例颗粒度组织章节；同类活动的旧标题是参考，不是强制照搬。
5. 产出一级标题；确实有多个相对独立的活动环节或工作环节时展开二级标题。
6. 仅对宽泛且确需解释的业务标题写简短内容方向；清晰的事实类标题不需要注释。未确定信息可留在相应部分供第二阶段口述补充，避免虚构实情。

## 4. 框架验收关注点

- 内容覆盖基本完整，能呈现由本次活动需求产生的主要信息层，包括实际适用的活动目标与内容、组织单位、时间地点、参与对象、工作安排、资源和注意事项等；不要求每种活动都设置全部常见标题。
- 一级、二级标题能反映活动的高层信息结构；不同业务板块按需要区分。具体操作、单个物品和时间点不为了变成目录而增设标题。
- 注释覆盖合理：含义清楚的基础标题不加冗余解释；对宽泛业务标题只在有帮助时简要说明内容方向；不确定的信息不靠注释猜定。
- 讨论阶段可以合并标题以便用户理解；正式策划案按适用案例拆分需要独立呈现的一级标题。
- 框架能够引导后续填充；用户可以在第二阶段自然口述补充，Skill 负责归入对应部分。
- 用户调整章节顺序、标题或内容后，后续撰写依据最新确认版推进。

以上为用户已确认的第一阶段验收依据。它关注内容覆盖和注释安排，不要求第一阶段补齐策划案具体细节。

## 5. 内部层级标签的当前决定

确认过的一级/二级标题及其所属正文需要在排版阶段可用。具体是在生成时隐含记录，还是用轻量 Markdown 标题、YAML、JSON 或其他方式传递，**当前不作强制技术规定**。在接口实施前，由 Codex 提出两种低成本方案并用样本测试；用户体验以直接阅读文章为优先。

## 6. 第二阶段的逐模块填写约定

- 按已确认框架逐个处理一级标题，每轮以一个主模块发问和推进。可优先从工作安排、材料准备、注意事项、人员安排等本次活动特有内容开始，再继续处理其余模块。
- 开始当前模块时，先询问用户希望写入哪些内容。用户可以口语或零散补充。
- AI 根据用户提供的信息整理当前模块，保留全部原意，仅作必要的语言规范化；不臆想、扩展或补入用户未表达的内容。歧义影响原意时，先针对当前模块澄清。
- 先展示当前主模块并与用户完成对齐。若同轮口述明确牵涉其他模块，在同一回复中再按框架顺序展示这些模块的相关内容供确认；不展示未受影响的其他模块或完整框架，也不补猜用户没有提供的内容。
- 因关联信息而确认过的模块，之后轮到它作为主模块时仍要专门询问用户希望写入什么；可以带入已确认信息并询问是否还需补充，不能跳过主模块询问。
- 全部模块完成专门询问和内容确认后，必须在对话框展示完整稿件，以便于阅读的普通文章形式呈现，不使用交接专用标记。等待用户确认全文；用户要求修改时，修改后重新展示完整稿并再次等待确认。
- 用户确认完整稿后，才依照 `formatting-skill-workspace/策划案格式交接规范.md` 生成 Markdown 交接稿。框架中的内容方向提示用于引导写作，不写入最终正文。交接规范文件规定格式，最终稿保存路径另定。
