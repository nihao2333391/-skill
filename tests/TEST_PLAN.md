# 测试执行方案

## A. 第一阶段（要求在开发时优先完成）

### CASE-01 输入部分信息
参照 `examples/teacher-day-input.md` 首轮。验收：框架覆盖献花、答题和实际给出的基础信息；只在宽泛业务标题确有帮助时加简短注释；未提供的规则、人员或价格不作猜测。

### CASE-02 信息增量
将 `teacher-day-input.md` 的第二轮信息加入。验收：答题规则在对应子章节变得更具体，已知约束不丢失。

### CASE-03 无历史同类策划案
参照 `examples/no-matching-case.md`。验收：业务框架针对交换业务，且没有招新专属章节。

### CASE-04 反向从案例学习
参照 `examples/recruitment-case.md`。验收：能解释原策划案各章服务于哪项业务目的，不把样例作为所有活动强制模板。

### CASE-05 用户修订提纲
输入：“背景和目的合成一节，新增单独的物资准备，把两个活动在同一章节下分开。”验收：框架修改准确，后续写作依据修订版。

### CASE-06 已知事实不得想象填充
初始不提供日期、主持人、奖品价格。验收：相关信息用“待确认”表示，建议方案与事实分开。

## B. 第二阶段

### CASE-07 框架引导下的口语补充
围绕教师节已确认框架，逐个一级标题进行口语补充，并优先处理本次活动特有内容。验收：AI 先询问当前主模块；如果用户一次口述牵涉多个模块，同一回复先展示当前主模块，再按框架顺序展示实际受影响模块供确认；之后这些模块仍须接受专门询问。AI 不臆想、扩展或补充用户未表达的信息。全部模块完成专门询问和确认后，展示便于阅读的完整稿，等待用户确认全文，再生成符合共同约定的 Markdown 交接稿。

### CASE-08 修改已定事实
用户修改地点、时间或活动机制。验收：仅更新受影响模块；完整稿确认前，重新展示修订后的全文并等待用户确认。用户确认后再生成交接稿。

## C. 第三阶段

### CASE-09 层级与顺序保持
从确认稿到排版输入再到 DOCX，验证每个标题及正文顺序。

### CASE-10 数字与字体
检查中英文混排、段落字号与固定行距，确认字体缺失时反馈。

### CASE-11 附件表格
基于招新策划案第四页，测试带合并/多列/多行的表格保留能力；原始电话不得外传到公开示例。
