# 策划案业务工作流

本流程采用项目用户确认的产品要求。第一阶段建立可读框架，第二阶段逐模块补充内容，最后交接给格式设置 Skill。用户只要求框架或某一模块时，完成该范围即可，不强行推进到全文和交接稿。

## 一、理解任务并生成讨论框架

从用户自然语言、已有策划案或其他材料中识别活动目标、已提出事项、已确认条件、硬性要求和未知信息。输入足以判断活动类型及主要事项时，直接提供针对性框架；只有缺失信息会改变活动主要结构时，才先提出少量核心问题。

先确定一级标题代表的主要业务信息层，再判断是否需要二级标题展开相对独立的活动或工作环节。不要把具体动作、单个物品和时间点都提升为标题。讨论框架可以合并相关信息层以降低理解成本；正式稿依据适用历史案例拆开需要独立呈现的一级标题。若活动涉及与学生会以外的单位沟通，按实际关系纳入主办、承办等组织单位信息。

框架以正常可读的标题和短注释呈现，例如：

```text
冬至包饺子活动策划案（框架）

一、活动背景及目的
二、活动时间、地点及参与对象
三、活动内容与流程
四、工作安排
　内容方向：说明活动准备、现场组织和结束整理怎样分工。
五、所需材料
　内容方向：根据实际制作方式列出食材、工具和场地用品。
六、活动注意事项
```

此例只说明展示方式，不是固定模板。时间、地点、背景、目的、参与对象等含义清楚的标题不加说明。只有对工作安排、材料等宽泛标题，简短方向能帮助用户理解时才添加；无法确定时省略。框架里的内容方向是后续引导，不写入最终策划案正文。

用户调整框架后，以最新确认版本为后续内容组织依据。

## 二、逐模块询问、整理和确认

按一级标题逐模块推进。可以优先从工作安排、材料准备、注意事项、人员安排等与本次活动具体情况密切相关的模块开始。每轮以一个主模块发问和推进：询问用户希望在该部分写入什么。用户可以口语或零散补充，无需掌握策划案专业知识，也无需按字段组织内容。

用户回答后，忠实整理全部相关信息，仅作必要的语言规范化。先展示当前主模块，请用户确认是否符合实际想法。遇到影响原意的歧义时，针对具体信息澄清；不得自行补猜。

### 一次口述牵涉多个模块时

如果用户同一轮口述明确包含其他模块的信息，在同一条回复中按以下顺序处理：

1. 先展示当前主模块的整理内容并请用户确认。
2. 再按框架顺序展示本轮实际牵涉的其他模块内容并请用户确认。
3. 不展示没有被本轮信息牵涉的模块，也不重贴完整框架。

例如，用户在“工作安排”模块补充：“第一组准备面皮和馅料，第二组负责现场包、煮饺子，第三组负责活动后清理，大家最后一起吃。”AI 先整理工作分工，再依框架顺序整理活动流程和所需材料。只呈现这段口述明确提供的信息，不增加未提及的流程、人数或物资。

因关联信息而确认过的模块，之后轮到它作为主模块时仍要专门询问。可以带入已确认的信息并问用户是否还需补充，不能因为先前确认过片段就跳过该模块的主模块询问。

当前主模块和本轮牵涉模块完成对齐后，再继续后续一级标题。用户提出修改时，更新相应内容，并重新展示受影响内容确认。

## 三、完整稿确认

所有一级标题都完成专门询问和内容确认后，必须在对话框展示便于阅读的完整稿件。它是完整文章，不是摘要；采用普通、人看起来舒服的稿件排版，不使用交接专用标记。

等待用户确认全文。用户提出修改时，更新相应内容，再展示修订后的完整稿并等待确认。只有用户确认全文后，才能生成 Markdown 交接稿。

## 四、生成交接稿

用户确认全文后，遵守开发公共材料中的[策划案格式交接规范](../../00-Skill开发公共材料/交接规范/策划案格式交接规范.md)，生成 UTF-8 Markdown 交接稿。该规范文件定义格式，不是最终策划案的保存位置。

交接稿应保留完整文字、顺序和标题层级，按共同约定使用：

- 主标题的 `【主标题开始】` 与 `【主标题结束】` 边界标记。
- 一级标题使用 `##` 和中文序号。
- 二级标题使用 `###` 和带括号的中文序号。
- 三级项使用段首阿拉伯数字和英文句点。
- 普通正文自然分段，落款使用约定标记。

不得把框架阶段的“内容方向”或“待补充”提示当作正文。交接稿只包含用户确认的内容；未确认信息不能伪装成事实。当前交接规范限定纯文字策划案，最多三级样式，表格、图片和附件正文不在该接口范围内。

该 Skill 负责策划案内容和 Markdown 交接稿。它不负责创建或格式化 DOCX。
