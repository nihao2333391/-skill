# 06 验收标准与需求可追踪矩阵

## 一、阶段 1：框架生成（第一优先级）

| 用例 | 对应需求 | 通过条件 |
|---|---|---|
| T01 部分信息启动 | R-01,R-03,R-04,R-12 | 根据已有活动目标和事项形成基本完整的高层信息框架；对宽泛业务标题的注释简洁、有帮助且不猜测 |
| T02 无同类案例 | R-02,R-10 | 不依赖相同活动历史材料也可形成可用提纲 |
| T03 本次任务强制要求 | R-03,R-05,R-12 | 用户明确的活动环节与上级要求被保留；涉及外部单位协调时，框架包含主办、承办等必要组织信息 |
| T04 框架调整 | R-05,R-06 | 增删合并标题后，后续撰写以新版本为准 |
| T05 事实与建议分离 | R-07 | 未提供的负责人、预算、时间等以待确认方式体现 |
| T06 适当颗粒度 | R-02,R-03 | 一级/必要二级标题清晰，工作步骤用正文/条目描述，不出现为凑数量拆标题 |
| T07 框架覆盖与注释 | R-04,R-12 | 主要信息层覆盖基本完整；含义清楚的基础标题无多余注释，宽泛业务标题按需给简短内容方向；讨论稿可合并相关层级 |

## 二、阶段 2：逐模块补充与确认

| 用例 | 对应需求 | 通过条件 |
|---|---|---|
| T08 逐模块填写与确认 | R-06,R-13 | Skill 先询问当前主模块；一次口述牵涉多个模块时，同一回复先展示主模块，再按顺序展示实际受影响模块供确认；这些模块之后仍须接受专门询问 |
| T09 任务变更 | R-05,R-06 | 修改一项活动机制后，受影响章节同步修订；其余章节保持稳定 |
| T10 忠实整理、全稿确认与交接 | R-07,R-08,R-13 | 不臆想、扩展或补充用户未表达的内容；全部模块完成专门询问和确认后展示便于阅读的完整稿，等待用户确认全文；确认后按共同约定生成 Markdown 交接稿 |

## 三、阶段 3：接口与排版

| 用例 | 对应需求 | 通过条件 |
|---|---|---|
| T11 层级交接 | R-08 | 主标题和各级标题能够由排版模块获得明确层级 |
| T12 全文完整性 | R-08,R-09 | 文稿的文字、标点、顺序和表格单元内容与 DOCX 输出一致 |
| T13 样式属性验证 | R-09 | 页边距、标题/正文字体字号、指定行距符合格式配置 |
| T14 可编辑文件 | R-09 | Word 正常打开；文本、表格可编辑，原始文稿保留 |
| T15 多宿主验证 | R-11 | 指定宿主能触发相同业务行为；实际缺少程序执行能力的宿主标注能力边界 |

## 四、验收证据

- 第一阶段：保存初始输入、完整框架、用户修改、最终框架的对话记录。
- 第二阶段：保存框架版本与对应确认正文，检查内容对齐。
- 第三阶段：保存结构化/内部表示的测试输出、生成 DOCX、格式属性检查报告、必要时 PDF 预览。

**迭代原则**：先把 T01—T07 作为真实可用的产品能力完成，再推进 T08—T10，最终做 T11—T15。
