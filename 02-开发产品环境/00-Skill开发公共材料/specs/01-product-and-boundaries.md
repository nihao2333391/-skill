# 01 产品目标与需求规格

## 1. 业务问题

学生会策划案已有较成熟的写作惯例。成员通常拿到的是任务而非完整文稿，例如“在教师节开展献花、答题，地点另有安排”。编写时需要覆盖符合学校惯例的项目与业务细节，再做内容组织，之后再按格式规范排版。传统流程的修改成本集中在**业务遗漏、框架反复变化、格式手工统一**。

## 2. 用户价值

- 更快地从不完整任务信息得到覆盖关键事项的可审核框架。
- 让提纲的颗粒度接近学校既有策划案：一二级标题按任务需要展开。
- 对话式补全活动内容，减少“为了填标题而写空话”的情况。
- 最后通过程序化处理形成可编辑 Word，同时保留确认稿的内容和阅读顺序。

## 3. 输入条件与预期输出

| 类型 | 描述 |
|---|---|
| 最小输入 | 活动目的或任务目标 + 大致要做的事情（两者可在对话中补齐） |
| 常见附加输入 | 上级要求、时间地点、参与人员、校区、已有确定方案、预算/物资、组织单位 |
| 可选参考 | 历史类似策划案、校内其他类策划案、规范 PDF |
| 首次核心输出 | 针对本任务的一级/必要的二级标题 + 各部分内容方向或待补事项 |
| 中期输出 | 按一级标题逐模块整理并经用户确认的内容 |
| 全稿预览 | 全部模块确认后，在对话框按便于阅读的形式展示完整稿件，等待用户确认 |
| 交接输出 | 用户确认全稿后，依照 `交接规范/策划案格式交接规范.md` 生成 Markdown 交接稿 |
| 最终输出 | 经确认的交接稿交给 DOCX 排版模块 |

## 4. 可追踪需求

| ID | 需求 | 优先级 |
|---|---|---|
| R-01 | 用户提供部分活动信息即可启动，提问围绕影响业务结构的核心缺口 | P0 |
| R-02 | 学习已有案例的常见章节、业务关切与信息颗粒度，并标记来源与适用范围 | P0 |
| R-03 | 对本次活动目的、任务事项、约束进行分析，生成任务适配的一级/二级标题 | P0 |
| R-04 | 对内容方向不明显的宽泛标题按需给出简短提示；含义清楚的标题无需注释，注释不得猜测方案 | P0 |
| R-05 | 用户可调整、增删、合并章节后再确认框架 | P0 |
| R-06 | 提纲确认后，按一级标题逐模块补齐内容；若一次口述牵涉多个模块，同一回复先展示主模块，再按顺序展示受影响模块供确认；每个模块之后仍须接受专门询问 | P0 |
| R-07 | 对未知活动事实清楚标记“待确认”，对推荐方案标记“建议”，不擅自确定 | P0 |
| R-08 | 所有模块完成专门询问和确认后，必须在对话框展示便于阅读的完整稿件；等待用户确认全文后，才按交接规范生成 Markdown 稿件 | P0 |
| R-09 | 根据外部样式规则程序化输出 DOCX，并检查指定属性 | P1 |
| R-10 | 参考素材可替换/增补，不把某一次活动的固定章节作为所有活动的强制表头 | P0 |
| R-11 | 采用可在多种 AI 宿主读取的说明文档/资源文件，必要程序按宿主能力运行 | P1 |
| R-12 | 第一阶段框架内容覆盖基本完整、注释合理；讨论稿可合并信息层，正式策划案按适用案例拆分独立一级标题 | P0 |
| R-13 | 第二阶段每次先询问当前主模块下要写入的内容；Skill 忠实整理用户提供的信息，只作必要语言规范化，不臆想、扩展或补充；当前主模块和同轮牵涉的其他模块分别确认，关联确认不代替后续专门询问 | P0 |

## 5. 需求质量定义

**框架质量**同时考量：（a）已知任务目标是否被覆盖；（b）关键实施链条是否完整；（c）有无无关冗余章节；（d）一级/二级标题是否符合当地写作惯例和描述颗粒度；（e）待确认事项是否能够用来推进活动决策。

**写作质量**看业务事实准确性、章节内容具体性与可提交性；**排版质量**看格式属性、内容顺序、全文一致性与可编辑性。
