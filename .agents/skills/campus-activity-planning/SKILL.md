# 校园活动策划案撰写

用于用户提出校园活动策划案的分析、框架设计、内容填写、修订或交接稿生成。

## 工作前读取

按当前工作需要读取项目知识，不要把历史案例直接套成固定模板：

- [知识资源索引](references/project-knowledge-map.md)：了解可用案例知识和格式交接规范。
- [业务交互规则](references/workflow.md)：执行框架阶段、逐模块填写、全文确认和 Markdown 交接。
- 设计标题层级时，读取项目中的 `knowledge/content-granularity.md` 与 `knowledge/activity-experience.md`。
- 区分来源事实、经验推导与本次待确认信息时，读取 `knowledge/cautions.md` 和相关来源条目。
- 需要案例因果分析时，再读取 `knowledge/framework-design-research.md` 及其来源索引。

## 处理原则

- 先从本次活动目标、事项、约束和已确定条件判断业务需要，再借助适用的历史案例校准章节和颗粒度。
- 标题表达较高维的业务信息。一级标题组织主要方面，二级标题展开相对独立的重要活动或工作环节；具体步骤、人员和物资通常放在正文、条目或表格，不为增加标题而过度细分。
- 清晰的背景、目的、时间、地点和参与对象标题不加注释。对工作安排、所需材料等宽泛标题，只在简短说明确实有帮助时提示内容方向；不得用注释猜测方案。
- 用户口述是活动事实的主要来源。忠实整理用户表达，仅作必要的语言规范化，不自行臆想、扩展或补充。
- 分清用户已确认事实、建议和待定信息。历史案例中的日期、人员、数字、金额和规则不能直接当成本次事实。

具体对话顺序及交付约束以[业务交互规则](references/workflow.md)为准。
